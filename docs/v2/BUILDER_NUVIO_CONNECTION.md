Nuvio issues an ordinary account token, not a read-only delegated token. Dingo limits its own endpoint use to this approved slice. Clearing Dingo's token does not revoke it server-side; its validity is governed by Nuvio. Same-origin script access remains part of the browser security boundary. Automated checks use the owner-approved mocked/local Nuvio boundary; owner-operated live acceptance is separate evidence. No security audit is claimed.

## Profile and pull contract

Profile selection retains account UUID, profile-row UUID and numeric index (1–6). Duplicate/malformed identities and owner mismatches are rejected; display names never identify a target. Protected profiles remain selectable, with a lock and “PIN protected” subline. Selecting one reveals one masked numeric PIN field, inline in the selected card from 900px and below the profile list on phone, outside the radio label. The shared Import/Send component automatically verifies exactly four ASCII numeric digits; there is no Verify button. One to three digits cause no request. Four-digit paste follows the same strict contract; mixed or overlong values are rejected without truncation. The field clears immediately before `{p_profile_id: index, p_pin}` is sent to `verify_profile_pin`; Dingo never persists, logs, exports or puts the PIN in a URL. **Checking PIN…** is announced in place. A valid single-row unlocked response records the existing exact grant and advances to the flow's normal safe-read Review, with no extra Continue step. Returning to profiles can show the retained **PIN verified** status and open lock.

Incorrect PIN clears and refocuses the enabled input after rendering, announces **Incorrect PIN. Try again.**, and waits for newly entered digits. Positive `retry_after_seconds` and profile lockout timestamps disable fresh entry until elapsed, with a local countdown and no polling or replay. A synchronous input-attempt guard and connection-level pending guard prevent duplicate fourth-digit, paste/input, Enter and rerender requests. Attempt-owned cancellation prevents late success/failure from granting another profile, advancing an abandoned view or clearing a newer draft. Target/account changes, disconnect/relogin, reset and unsubmitted protection changes clear drafts; responsive relocation also clears a draft without discarding an established grant. Only authoritative attempts may update UI or grants; existing identity/protection and lockout rules remain in force.

Unlocks remain private in memory for the exact account/row/index. Disconnect, re-login, expiry and reload clear them. Profile retrieval prunes removed/replaced identities and changed protection metadata. Because the API does not expose a separate PIN revision, changed `updated_at` on a protected profile conservatively requires verification again; the verification RPC's own timestamp/lockout reset is accepted only after an identity check. Unknown protection metadata remains unavailable. The Collection pull endpoint does not enforce the PIN: Dingo deliberately honors the same verification RPC used by official clients, without their offline PIN cache/fallback.

The current-user/profile reads before and after the Collection RPC must agree on account and selected profile identity/index, and establish that the profile remains unprotected or has a current matching PIN verification. Removal, slot replacement, account changes or discovered protection changes invalidate the pull. Cancellation, disconnect and newer operations invalidate older responses, even if a transport fails to honor cancellation. These bounded checks detect changes observed during the request; they are not a transactional server revision lock.

`sync_pull_collections` receives `{p_profile_id: index}`. Zero rows mean **no stored blob**. One matching row with `collections_json: []` means **explicitly empty Collections**. Both are shown distinctly and cannot import or clear current work. Multiple rows, mismatched profile indices, non-array JSON and importer structural errors fail closed.

The existing preservation-first importer validates a detached view. Counts use its authoritative Collection/Folder/Source hierarchy; legacy `catalogSources` entries are preserved and disclosed, not counted as active Sources or silently migrated. The retrieved array itself is cloned and deeply frozen without normalization, additional fields or serialization through the canonical exporter.

## Reviewed snapshot and local import

Once a pull has completed structural validation and captured the reviewed immutable snapshot, importing is entirely local. It makes no requests, performs no second account/profile check and never silently refreshes data. Token expiry keeps all local modes available; login is required for the next network operation. Explicit disconnect discards connection/review state.

Review binds the snapshot and destination project. Changed project content requires another review; selection/diagnostic changes alone do not invalidate it. Existing work requires one explicit mode:

- **Add as separate Collections:** append every incoming Collection intact without matching or deduplication. Existing settings, order and selection remain; incoming missing/conflicting IDs are repaired against current IDs.
- **Merge exact matches:** use the pure `planCollectionMerge` planner for both preview and the narrow atomic `mergeImportedCollections` controller operation.
- **Replace current project:** retain explicit destructive confirmation and the existing dirty-protected replacement pipeline. The imported project starts clean.

Empty work does not force mode selection. All modes reuse the existing importer; the reviewed raw array is unchanged.

## Conservative local merge

Collections match only when both titles pass `isValidVisibleNuvioTitle`, the strings are exactly equal, and that title occurs once in both sibling lists. There is no case, whitespace, punctuation, plural, article, fuzzy, ID or provenance matching. Duplicate exact titles are ambiguous and incoming nodes append separately.

Invisible titles, including single/repeated U+200E, blank, malformed and other non-visible values, never match. An unmatched Collection stays whole; its children are never considered for merge. A visible title hidden only through presentation settings remains eligible. Folders use the same exact/visible/unique rule, only inside a safely matched Collection; unmatched/invisible/ambiguous Folders remain whole, with no Source dedupe.

Existing matched Collection/Folder own settings and raw preservation data win, including artwork. Incoming artwork does not fill blank or absent artwork on a matched existing node. Only eligible children are integrated; unmatched imported nodes retain their incoming artwork and other importer-preserved fields. No configurable artwork-precedence option is implemented. Existing order at every level stays fixed; unmatched children append in incoming order.

Source comparison is confined to matched Folders. It reuses the existing source editor family duplicate/identity contract and the normal Source serializer overlay. Comparable Sources require the same family/key plus equal complete serialized content, including exact title, configuration and unknown fields. This is intentionally conservative: even some family-equivalent defaults remain separate when their full preserved representations differ. Non-comparable/opaque Sources require safely serialized exact preserved equality; invalid or uncertain comparisons retain both. Object key order does not matter, array order does. The existing Source survives when a duplicate is skipped.

The planner imports and validates the complete input, builds a detached candidate, validates Builder identities, reserves every destination Nuvio ID, repairs only inserted Collection/Folder IDs and validates the final tree. Existing IDs never change. Preview consumes only local preview factories and mutates nothing. Apply uses controller factories, commits once, marks dirty and retains valid selection. Any failure returns diagnostics without changing any controller state or revision. A successful all-duplicate merge still advances one revision. No provenance metadata is created.

The Merge preview reports Collections/Folders merged, duplicate Sources skipped and Collections/Folders/Sources added from that same planner. Ambiguous matches count as additions. It states: “Only exact visible names are matched. Similar or hidden names stay separate.”

## Read-only Import and Send boundary

There is no import-time backup action or filename helper. Ordinary **Download JSON** and **Copy JSON** retain their existing behavior and require no Nuvio connection.

**Current Send contract:** Replace-only for one selected profile using the complete frozen canonical proposal P. Review captures the identity-bound remote baseline R0. Choosing **Replace Collections** acquires the duplicate-operation guard, checks project freshness and current profile/PIN authority, then performs a fresh identity-bound pull R1. R1 must equal R0 in full before the final synchronous guard permits one push. Any change, including a timestamp-only change or a change to P, stops and requires fresh Review. No automatic write retry or restore is permitted; acknowledgement and readback remain distinct. No supported CAS/expected-revision API is evidenced, so the accepted final-read → write-commit race remains. Remote Add/Merge/selected modes stay deferred. Call this Send, not Sync.

**One optional current-Nuvio backup:** Review offers **Download current Nuvio backup**, recommended but never required for Replace. It contains only the exact reviewed raw R0 inner Collections array, with no canonicalization, authentication, diagnostics or account envelope. Missing remote rows retain `blobPresent: false` privately and download `[]`; that file represents empty contents, not database-row absence. Its timestamp comes from the immutable Review capture, and its filename/bytes remain stable for that Review. Retrying makes no request and does not affect the Send state. Feedback says **Backup download started**, without claiming the file was saved. A new Review provides its own descriptor. If replacement proceeds, R1 == R0 establishes that the optional backup represents the immediately preceding observed state.

Optional backup is a Review utility using the ordinary single-file Export adapter. There is no mandatory recovery stage, proposed-replacement download or possession confirmation. The proposed payload remains available through manual Download JSON and Copy JSON.

The normal write sequence is `PREPARED → REVIEWED (R0) → PREFLIGHT (R1) → DISPATCHING → ACKNOWLEDGED/OUTCOME_UNKNOWN → VERIFYING`, then the appropriate result. Backup preparation/initiation failure remains local feedback and cannot disable Replace or change coordinator state.

The sole write operation is `POST https://api.nuvio.tv/rest/v1/rpc/sync_push_collections`, with `{p_profile_id: numericIndex, p_collections_json: completeArray}`. HTTP 204 acknowledges the void RPC without JSON parsing. Transport returns separate `not-sent`, `rejected`, `acknowledged` or `unknown` evidence, with dispatch flag/status/safe error code. Known request/access/rate-limit rejections are retained; 5xx, unexpected responses and network/timeout/abort after dispatch remain uncertain. There is **no write retry**, including 429/503, and no automatic restore. Existing bounded safe-read retries are unchanged.

Readback compares the same frozen intended array against a freshly identity-bound pull. `VERIFIED` means intended contents were observed; a 204 remains acknowledged even if readback is different or unavailable. An uncertain dispatch retains its proposal, target, baseline and dispatch evidence for the page lifetime, across closure, disconnect/reconnect and local project changes. Observing previous or third-party contents does not prove the write never happened and does not release the unresolved-attempt block. Only observing intended contents resolves that block; **Check Nuvio again** performs reads only, with current access to the exact original account/row/index. It never resends. Cancellation before dispatch prevents the push; genuine view interruption after dispatch cannot erase evidence or stop verification. The visible UI prevents ordinary dismissal during active checking/sending/verifying. Application teardown may abort transport but cannot undo a dispatched write.
