## Supported flow

**Import / Open an existing collection** offers three method buttons: **Import from Nuvio**, **Import from file** and **Import from JSON**. Home initially shows **Choose an import method** with muted guidance inside the common method panel. The compact method controls reuse the existing import-action secondary style paired with Create: shared geometry, typography, hover and transitions, with a quieter Builder cyan surface. They retain a primary label and muted supporting line, and no generic icons. File/JSON selection retains a dark Builder surface, restrained cyan tint, stronger cyan border and the shared structural inset. The quiet empty state has no icon or repeated method descriptions. Nuvio uses the same Builder colours as the local import methods, retaining its dialog trigger semantics and a small decorative forward chevron without a persistent selected state. Desktop (900px and wider) uses a 270px method column and places the selected local form to the right of a structural divider, in a panel with a 328px minimum height. Ordinary method states retain that footprint; the JSON field starts at 112px and scrolls internally while remaining vertically resizable. Mobile stacks the form beneath the buttons with natural panel height and a taller JSON field. Switching methods retains the chosen native file and pasted draft, and hidden forms cannot receive focus or submit. The shared busy guard locks all method changes. Nuvio opens the existing dialog immediately; closing restores the trigger, selected method and drafts. Its non-interactive journey indicator reads **Connect › Select profile › Review**: cyan/emphasized current stage, readable completed stages, muted future stages and subtle separators. It has no visible numbering or underline, wraps when necessary and preserves the deliberate Back behavior. Nuvio import is also available in the workspace. The native file picker is the sole visible filename display. Connect with a Nuvio email/password, choose one eligible profile, load its Collections and review the profile, counts, import notices and remote update time. Connection remains optional: manual JSON import, Copy JSON and Download JSON keep their existing behavior.

The connection uses the browser-direct API at `https://api.nuvio.tv`. Dingo's Worker never receives Nuvio credentials. A small framework-independent transport has a fixed allowlist: password login, current user, `sync_pull_profiles`, `verify_profile_pin` and `sync_pull_collections`. Requests omit cookies, bypass browser response caching and reject redirects. Account, profile and Collection reads may retry once after HTTP 429 or 503; login and PIN verification are never automatically replayed. Retry waits remain cancellable and respect readable numeric or HTTP-date `Retry-After` values up to 30 seconds. Missing, invalid or elapsed values use a 2-second fallback; longer valid cooldowns return an error for manual retry instead of retrying early. Every attempt retains the normal 20,000 ms request timeout. There are no remote Collection writes, background requests, new dependencies or Worker changes. The owner-approved PIN RPC can update Nuvio's PIN-attempt/lockout metadata; it does not edit Collections.

The access token and its expiry are private in-memory connection state, separate from the Builder project. Password fields clear on submission; passwords, access tokens and raw auth responses are not placed in Builder state, browser storage, URLs, diagnostics, logs, analytics or exports. Refresh tokens are discarded. Reload starts disconnected. Expiry clears the access token and requires login for the next network operation. Closing the dialog cancels pending requests and clears form/review state, while retaining an unexpired connection. Disconnect explicitly discards the connection, profiles and review without changing the Builder project or issuing any logout request.

Nuvio issues an ordinary account token, not a read-only delegated token. Dingo limits its own endpoint use to this approved slice. Clearing Dingo's token does not revoke it server-side; its validity is governed by Nuvio. Same-origin script access remains part of the browser security boundary. The owner reported successful live login, profile avatars, PIN verification, Collection import, backup, local Add/Replace and transient success feedback after pass 2. Earlier automated checks were mocked/local; no security audit is claimed.

## Profile and pull contract

Profile selection retains account UUID, profile-row UUID and numeric index (1–6). Duplicate/malformed identities and owner mismatches are rejected; display names never identify a target. Protected profiles remain selectable, with a lock and “PIN protected” subline. Selecting one reveals a four-digit password-style numeric PIN field. At the shared 900px desktop breakpoint, this field and **Verify** sit inside the selected profile card, alongside its small avatar, name and metadata. Normal cards retain their compact height; actionable PIN errors/lockouts can wrap below the controls. Success replaces the controls with **PIN verified** and an open padlock. Mobile retains the separate PIN panel below the profile list and **Verify PIN** label. Exactly one PIN form is mounted, outside the profile radio label; changing responsive layout clears unsubmitted digits without discarding a verified unlock. **Verify** / **Verify PIN** sends `{p_profile_id: index, p_pin}` directly to the authenticated `verify_profile_pin` RPC. The field clears immediately on submission; Dingo never persists, logs, exports or puts the PIN in a URL. Only a single valid result row with `unlocked: true` authorizes loading. Incorrect attempts remain locked; positive `retry_after_seconds` and profile lockout timestamps prevent another attempt until elapsed, with a local countdown and no polling.

Unlocks remain private in memory for the exact account/row/index. Disconnect, re-login, expiry and reload clear them. Profile retrieval prunes removed/replaced identities and changed protection metadata. Because the API does not expose a separate PIN revision, changed `updated_at` on a protected profile conservatively requires verification again; the verification RPC's own timestamp/lockout reset is accepted only after an identity check. Unknown protection metadata remains unavailable. The Collection pull endpoint does not enforce the PIN: Dingo deliberately honors the same verification RPC used by official clients, without their offline PIN cache/fallback.

The current-user/profile reads before and after the Collection RPC must agree on account and selected profile identity/index, and establish that the profile remains unprotected or has a current matching PIN verification. Removal, slot replacement, account changes or discovered protection changes invalidate the pull. Cancellation, disconnect and newer operations invalidate older responses, even if a transport fails to honor cancellation. These bounded checks detect changes observed during the request; they are not a transactional server revision lock.

`sync_pull_collections` receives `{p_profile_id: index}`. Zero rows mean **no stored blob**. One matching row with `collections_json: []` means **explicitly empty Collections**. Both are shown distinctly and cannot import or clear current work. Multiple rows, mismatched profile indices, non-array JSON and importer structural errors fail closed.

The existing preservation-first importer validates a detached view. Counts use its authoritative Collection/Folder/Source hierarchy; legacy `catalogSources` entries are preserved and disclosed, not counted as active Sources or silently migrated. The retrieved array itself is cloned and deeply frozen without normalization, additional fields or serialization through the canonical exporter.

## Reviewed snapshot and local import

Once a pull has completed structural validation and captured the reviewed immutable snapshot, importing is entirely local. It makes no requests, performs no second account/profile check and never silently refreshes data. Token expiry keeps all local modes available; login is required for the next network operation. Explicit disconnect discards connection/review state.

Review binds the snapshot and destination project. Changed project content requires another review; selection/diagnostic changes alone do not invalidate it. Existing work requires one explicit mode:

- **Add as separate Collections:** append every incoming Collection intact without matching or deduplication. Existing settings, order and selection remain; incoming missing/conflicting IDs are repaired against current IDs.
- **Merge exact matches:** use the pure `planCollectionMerge` planner for both preview and the narrow atomic `mergeImportedCollections` controller operation.
- **Replace current project:** retain explicit destructive confirmation and the existing dirty-protected replacement pipeline. The imported project starts clean.

Empty work does not force mode selection. All modes reuse the existing importer; the reviewed raw array is unchanged.

## Conservative local merge

Collections match only when both titles pass `isValidVisibleNuvioTitle`, the strings are exactly equal, and that title occurs once in both sibling lists. There is no case, whitespace, punctuation, plural, article, fuzzy, ID or provenance matching. Duplicate exact titles are ambiguous and incoming nodes append separately.

Invisible titles, including single/repeated U+200E, blank, malformed and other non-visible values, never match. An unmatched Collection stays whole; its children are never considered for merge. A visible title hidden only through presentation settings remains eligible. Folders use the same exact/visible/unique rule, only inside a safely matched Collection; unmatched/invisible/ambiguous Folders remain whole, with no Source dedupe.

Existing matched Collection/Folder own settings and raw preservation data win. Only eligible children are integrated. Entire new nodes retain importer-preserved fields. Existing order at every level stays fixed; unmatched children append in incoming order.

Source comparison is confined to matched Folders. It reuses the existing source editor family duplicate/identity contract and the normal Source serializer overlay. Comparable Sources require the same family/key plus equal complete serialized content, including exact title, configuration and unknown fields. This is intentionally conservative: even some family-equivalent defaults remain separate when their full preserved representations differ. Non-comparable/opaque Sources require safely serialized exact preserved equality; invalid or uncertain comparisons retain both. Object key order does not matter, array order does. The existing Source survives when a duplicate is skipped.

The planner imports and validates the complete input, builds a detached candidate, validates Builder identities, reserves every destination Nuvio ID, repairs only inserted Collection/Folder IDs and validates the final tree. Existing IDs never change. Preview consumes only local preview factories and mutates nothing. Apply uses controller factories, commits once, marks dirty and retains valid selection. Any failure returns diagnostics without changing any controller state or revision. A successful all-duplicate merge still advances one revision. No provenance metadata is created.

The Merge preview reports Collections/Folders merged, duplicate Sources skipped and Collections/Folders/Sources added from that same planner. Ambiguous matches count as additions. It states: “Only exact visible names are matched. Similar or hidden names stay separate.”

## Read-only import and future Send boundary

There is no import-time backup action or filename helper. Ordinary **Export collections**, Copy JSON and Download JSON retain their existing behavior.

**Owner-approved future direction — not implemented:** the first **Send to Nuvio** write slice is Replace-only for one selected profile, using the complete canonical Dingo Collection array. It requires explicit destructive review, current Dingo PIN verification for protected profiles, a final fresh remote comparison against the reviewed baseline, no automatic write replay after an uncertain outcome, and post-write readback verification. An observed remote change stops the write and requires renewed review. No supported CAS/expected-revision API has been evidenced; the owner accepts the remaining final-read → write race with these mitigations. Call this Send, not Sync. Remote Add, Merge and selected-Collection modes remain deferred.

**Mandatory dual recovery downloads before any future push:** automatically initiate downloads of both (1) the fresh current remote inner `collections_json` array and (2) the exact proposed Dingo replacement array. If either preparation or download initiation fails, no write occurs. The same semantic proposed payload must be used for review, the proposed JSON download, push and post-write verification. Download initiation cannot prove that the user retained either file; neither download removes the server concurrency limitation.

The approved future **Export & Send** concept and permanent manual alternatives are recorded in the [export direction](./BUILDER_EXPORT.md#future-send-to-nuvio). These are product requirements for a separately scoped implementation, not current UI, transport or remote-write behavior.

The TV/Mobile repositories declare GPL-3.0; the inspected self-host repository declares Apache-2.0. This client/server evidence supports the owner-approved PIN extension; the public API document did not separately document it. No substantive upstream code or offline PIN implementation was copied.
